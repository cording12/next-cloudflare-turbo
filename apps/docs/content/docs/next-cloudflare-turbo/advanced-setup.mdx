With the basic setup of Next-Cloudflare-Turbo done, this section covers more advanced configurations that see the implementation of separate `staging` and `production` environments, as well as configuring caching for use with Next.js revalidation and caching.

The caching system uses:
- **D1**: Stores cache tags for on-demand revalidation
- **R2**: Stores incremental cache data (pages, API responses)  
- **Durable Objects**: Manages cache invalidation queues

## Creating databases
The [manual setup](/next-cloudflare-turbo/manual-setup) will guide you through creating D1 databases. The process is the same for R2. In this instance, you will need to create four D1 databases, and two R2 buckets. The commands would be

D1 databases for application data:
```npm title="apps/app"
npx wrangler d1 create your-database-name
npx wrangler d1 create your-database-name-staging
```

D1 databases for tags caches:
```npm title="apps/app"
npx wrangler d1 create your-database-name-tag
npx wrangler d1 create your-database-name-tag-staging
```

R2 buckets for incremental cache:
```npm title="apps/app"
npx wrangler r2 bucket create your-bucket-name
npx wrangler r2 bucket create your-bucket-name-staging
```

<Callout>Don't forget to run `npm run cf-typegen` to ensure the bindings are accessible when using `getCloudflareContext()`</Callout>

## Creating environments

When you create an environment, Cloudflare effectively creates a new Worker with the name `top-level-name-environment-name`. For example, a Worker project named `my-worker` with an environment `staging` would deploy as a Worker named `my-worker-staging`.

Creating environments is as simple as adding the environment to the `env` key in your `wrangler.jsonc`:

```json title="wrangler.jsonc"
  "env": {
    "staging": {}
  }
```

## Working with environments

In the [manual setup](/next-cloudflare-turbo/manual-setup) page, you can see how we use `wrangler` commands to create D1 databases, apply migrations, and seed data. 

To change between environments, you simply pass a `--env` key to the CLI command, followed by the environment name.

For example:
```npm title="apps/app"
npx wrangler d1 migrations apply YOUR_DATABASE_NAME_STAGING --env staging --remote
```

This command would apply migrations to your remote staging database.

<Callout>The `--remote` flag should be used to execute `wrangler` commands against the remote resource (whether that's D1 or R2)</Callout>

## Configuring caches 

The advanced wrangler configuration should work out-the-box, however you will also need to modify the `open-next.config.ts` in the `apps/app` folder.

```typescript title="open-next.config.ts"
import { defineCloudflareConfig } from "@opennextjs/cloudflare"
import r2IncrementalCache from "@opennextjs/cloudflare/overrides/incremental-cache/r2-incremental-cache"
import doQueue from "@opennextjs/cloudflare/overrides/queue/do-queue"
import d1NextTagCache from "@opennextjs/cloudflare/overrides/tag-cache/d1-next-tag-cache"

/**
 * Cloudflare config implementing caching
 * See: https://opennext.js.org/cloudflare/caching
 */
export default defineCloudflareConfig({
// Incremental cache using R2
incrementalCache: r2IncrementalCache,
queue: doQueue,

// This is used for on-demand revalidation, i.e. revalidatePath/revalidateTag
tagCache: d1NextTagCache,

// Disable this if you want to use PPR
// See: https://nextjs.org/docs/app/getting-started/partial-prerendering
enableCacheInterception: true,
})

```

## Deploying to environments
If you're using the `package-advanced.json`, you can simply use the convenience scripts to deploy to staging or production:

```npm title="apps/app"
npm run deploy:staging
npm run deploy
```

These are wrapping the following commands:
```npm title="apps/app"
npx opennextjs-cloudflare build && opennextjs-cloudflare deploy --env staging
npx opennextjs-cloudflare build && opennextjs-cloudflare deploy --env production
```

## FAQ

<Accordions>
  <Accordion title="Why is there no Durable Object configuration at the top-level of the wrangler.jsonc?">
    Durable Objects don't work natively in local development. As a result, there is no point configuring them at the top-level when they cannot be used. The staging and production configurations, however, will work. This is explained in more detail in the OpenNext [Known issues](https://opennext.js.org/cloudflare/known-issues) page.  
  </Accordion>

  <Accordion title="What if I don't want one of the environments?">
    If you don't want one of the environments, staging for example, you can simply delete any `staging` related configurations. These would need to be removed from the `wrangler.jsonc` and `package.json` scripts (if you're using the advanced config).

    If you have already created the relevant resources (D1/R2), you can delete any of the resources via the Cloudflare Dashboard, or using `wrangler` commands.  
  </Accordion>

  <Accordion title="How do I handle environment variables across environments?">
    Use `wrangler secret` commands with the `--env` flag:
    ```bash title="apps/app"
    # Set secrets per environment
    npx wrangler secret put API_KEY --env staging
    npx wrangler secret put API_KEY --env production
    ```
    For non-sensitive variables, add them to the respective `env` sections in `wrangler.jsonc`.
  </Accordion>

  <Accordion title="My deployment failed with 'binding not found' errors. What's wrong?">
    This usually means:
    1. You haven't created the D1/R2 resources yet
    2. The resource IDs in `wrangler.jsonc` don't match your actual resources
    3. You're deploying to the wrong environment
    
    Run `wrangler d1 list` and `wrangler r2 bucket list` to verify your resources exist and their names match your configuration.
  </Accordion>

  <Accordion title="Can I use a different custom domain setup?">
    Yes. The `routes` configuration in the production environment can be modified:
    ```json title="wrangler.jsonc"
    "routes": [
      { "pattern": "your-domain.com", "custom_domain": true },
      { "pattern": "www.your-domain.com", "custom_domain": true }
    ]
    ```
    You'll need to configure the domain in your Cloudflare dashboard first.
  </Accordion>  
</Accordions>
